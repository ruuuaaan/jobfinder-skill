# 预算、轮转与恢复（新任务 CN_MAINLAND-4.0；旧任务保留 3.9）

Skill/CLI 的旧共享模式基础默认是每城 40 次实际搜索；网页版新建任务的默认渠道分配按下节执行，不把旧默认数字当作可用的分配结果。企业数和 HTTP 总请求数为 JSON `null`。显式有限配置仍有效；旧配置不会自动迁移，保留旧计划和进度的指纹与语义，不把旧证据日期改成当前日期。

## 网页默认渠道分配与一次性失败补充（2026-10-29）

新网页任务显式保存 `budget_policy=official_priority_once`。分配公式唯一来源是 `jobfinder/search_budget.py`；保存到 `effective_search_spec.search_budget.allocation_policy` 及 `per_city_channel`。每城已选的非官网渠道默认各分配 **5 次**（`BASE_OTHER`），也可在 `search_budget.per_channel` 里逐渠道显式指定额度；官网永远取剩余（城市总预算 − 其它渠道合计），**不接受单独指定官网额度**。没有启用官网时，剩余保留为未分配，不擅自开启渠道；基础预算不足各渠道额度合计时要求提高预算或减少渠道，不静默增加基础总额。

换算示例：8 个渠道（官网 + 猎聘/BOSS/智联/前程无忧/高校就业网/本地宝网站/本地宝公众号）、每城 60 次、非官网各 5 次 → 其它渠道合计 35，官网得 25。若仍用每城 40，则官网只剩 5，必须先提高城市总预算。

### 控制器侧的 `budget.per_channel`（与上面不同）

网页版是"官网取剩余"的分配法；**核心控制器的 `budget.per_channel` 是各渠道独立定额、互不侵占**：

```json
"budget": {"searches_per_city": 45,
           "per_channel": {"official_career": 10, "51job": 5, "zhaopin": 5, "boss": 5,
                           "liepin": 5, "campus_job": 5, "bendibao_web": 5, "bendibao_wechat": 5}}
```

- 某渠道配额用完 → 该渠道 `record-action` 被拒收，剩余任务在 `close-stage` 时转 `budget_exhausted`（计缺口，不影响其他渠道）。
- `searches_per_city` 在分渠道模式下不再限制总量，建议填成各配额之和，仅作展示与旧逻辑兜底。
- 阶段配额 `by_stage` 仍单独记，官网核实任务按官网阶段账判断（见 0.5.3）。

每城每个非官网渠道在首次**搜索尝试失败**时额外授予1次；不从官网扣除，不退款原失败消耗，后续失败不再授予。官网失败、搜索成功但零结果、网页读取/模型提取失败不触发。补充事件保存在 `channel_budget_grants`，记录城市、渠道、查询、尝试序号、失败类型和时间；暂停、恢复、手动重试、更改基础上限都不清零。补额度不解除服务不可用或验证限制。

例如每城基础50次并启用全部10个渠道：官网5次，其余9个渠道各5次（官网优先下已无剩余可分配，实际应先提高预算）；最多额外9次，总计最多59次。重试、备用搜索与新查询共同使用该渠道额度；有失败的非官网渠道最多6次（5+1）。补充后仍受页面、模型、时长及可执行查询数量限制，不保证必须花完。

运行与恢复由 `jobfinder_web/channel_budget.py`、`search_execution.py` 控制，网页显示基础、已补充、当前可执行及最大上限。没有政策字段的旧任务/API请求继续使用 `shared`，不静默迁移；已有任务不通过预算调整切换政策。Skill 代理执行这类网页任务时消费保存的分配和补充账本；CLI独立采集尚未自动发放这类补充，不将手动操作冒充自动执行。

## 旧共享模式与核心读取预算

岗位发现、目录搜索、企业补搜、失效回退共同扣该城的 40 次。列表页直读按页计（一页一条 `browse_list` 任务 = 1 次），官网招聘页用浏览器读取同样按页计（读一页 = 1 次），研究型检索任务（`route=research`）按条计；这三类都是计划里的任务，走同一条预算账。已实际执行的 success、failed、restricted 均计数，not_run 不计数。知识库入口复用本身不占搜索次数，读取网页仍计 HTTP；复用失效后的新搜索扣剩余额度。不能绕过计划再送一轮。未执行的计划不等于已搜索，不保证每城都用满 40 次；不限企业不解除 40 次搜索上限。

企业仅来自本轮相关线索、明确选择或有岗位/城市关联证据的知识库记录。企业名归一后每城去重。知识库资料不足的记录保留待核查，不因数量不限自动遍历整库；不得自动扩展集团、子公司或全国企业名单。

HTTP 实际请求（含 robots、导航、重定向、失败和有限重试）都记录。无限时每城额度为 null；有限总量仍按城市均分、余数给前面的城市，再扣该城已用量。候选归属其首个目标城市；跨城共用已读页面不重复计 HTTP，实际请求记在首次读取城市。企业计数是进入处理的具名候选去重数，不代表已核验成功企业数。保留 URL/接口审核、robots、限速、单请求超时、响应体积、有限重试；403/登录/验证码/429/TLS 受阻停止该站本轮请求，其他企业继续。Moka 已审核只读契约保留，其他站不获得任意接口调用许可。

Python 按城市轮转，每城候选也轮转；一次推进一个列表/详情步骤，首页导航及单步所需 robots、重试是有限的准备工作，不是严格等时调度。每步原子保存 traversal-progress.json，开始和异常退出也保存。只在原页面末页/总量等证据成立时标完成；重复响应、分页循环、连续 3 页没有新增原始岗位或详情链接均保留未完成。新增但不符合筛选的岗位也算加载进展，不能因为连续无匹配岗位就宣布翻完。

resume-traversal 默认 remaining：保留已用搜索/HTTP/企业计数，只继续未完成范围；不限量保持 null，有限量扣除实际消耗，已完成原文不重读。new_run 明确开启新预算计数，但仍不重做已完成遍历。remaining 保留该轮受限站点停止状态；新一轮可按原安全规则重试未完成任务。配置或规则改变必须重新生成计划/进度，不篡改指纹强行恢复。

动态浏览器也须遵守相同城市/企业范围、访问限制、加载进展和末页证据规则，保存页面及未完成进度。脚本可逐企业推进、同会话显式重试；不等于已接入Python的城市轮转、请求计量或原生恢复。浏览器实际搜索/企业处理、动作与快照单独记录，未取得内部网络日志时HTTP请求量写“未知/未计量”；处理回执的Python HTTP=0不能当浏览器请求量。有限预算下不能证明剩余额度足够就暂停依赖该额度的读取。HTTP中的requires_browser任务可另按[浏览器流程](browser-collection.md)执行并保存独立结论，不改写原HTTP进度。

双城示例：广州、深圳各有 40 次搜索，合计最多 80 次；广州已用 39 次后只剩 1 次回退搜索，深圳已用 36 次则剩 4 次，互不挪用。两城本轮相关企业和 HTTP 均无固定数量上限，交替推进并记录实际消耗。显式 HTTP 总量 21 时仍分广州 11、深圳 10；若广州已用 8、深圳已用 6，remaining 只剩 3、4。

## 网页搜索服务故障隔离

执行定义集中在 `jobfinder_web/search_execution.py`，参数来自 `jobfinder/spec.py:ProviderPolicy`，此文不另设参数。自动模式默认允许模型联网与本地浏览器，Tavily 只有本轮显式启用且已配置测试后参与。单服务模式默认只启用该服务，界面可勾选备用服务。站内搜索仍由显式 onsite_search 控制。

逐次 attempts 保存查询、渠道、城市、服务、序号、起止时间、结果、失败类别/原因、备用服务及回执。失败、备用请求、重试都扣城市/渠道搜索预算；有模型调用的搜索还扣模型预算。配置未完成的服务跳过，不虚增消耗。

网络临时错误、限流、服务临时不可用可以有限重试；认证/配置错误、浏览器缺失与登录验证停止该服务，等待明确重试或配置修复。连续失败达到阈值进入冷却；冷却后最多有限探测，不逐条查询重复撞同一服务。单条查询已尝试完允许路径则 failed，继续其他查询。搜索全不可用先处理剩余页面和已读批次；所有可执行工作耗尽时 partial 并明确“没有可用 Search Provider”。人工暂停、进程中断、全局时长/页面/模型额度仍分别保留原状态含义。

普通继续保留健康状态和累计用量；用户明确“重试”可重新启用服务，原失败 attempts 不删除。模型密钥和原始接口错误正文不写入尝试账本。

## 与运行控制器的关系（workflow-1）

- 预算账本挂在运行（`run_id`）上，**阶段切换不清零额度**：`close_stage` 只改阶段状态，`budget_used` 连续累计。
- 只有 `record-action` 里 `status ∈ success/failed/restricted` 的真实执行才扣次数；`skip`/`blocked`/`not_run` 不扣。
- 同一回执重复提交幂等，不重复扣费；`start-run` 时若带 `budget_used`（接续旧运行），继续在原配额上累加，不重开额度。
- 阶段受阻或用户跳过会保留缺口，并在 `finalize` 中把整轮判为 `PARTIAL`，不会因为进入下一阶段而"抹平"上一阶段的缺口。
- 预算耗尽的任务标 `budget_exhausted`，属于终止态：它让流程可以继续，但不算完成。
